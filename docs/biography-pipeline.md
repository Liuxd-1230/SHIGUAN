# 史官 SHIGUAN —— 传记生成管线

本文档定义从"标准人物档案"到"可发布传记"的完整生成管线，重点是如何在**不虚构**的前提下，把游戏数据写成有历史感的白话纪传体。管线对应产品规范第四节的八步，并在 Phase 3 实现。

---

## 0. 总原则：证据驱动，拒绝编造

- 传记的每一个重要段落都必须能追溯到 `TimelineEvent`。
- 模型只能基于**压缩后的结构化档案**写作，禁止访问原始存档原始字符串。
- 严禁：虚构对白、描写无证据的内心活动、凭空创造战役细节、为文学效果篡改时间与关系。
- `confidence` 决定模型能如何使用一条信息：
  - `confirmed`：可当作确定事实陈述。
  - `inferred`：可合理表述为"可能/大约/据推断"，**不得写成确定事实**。
  - `uncertain`：默认不在正文中陈述；仅在"不确定信息提示"面板展示，或谨慎以"史载不详"带过。

---

## 1. 管线八步

```
Profile ──▶ Timeline ──▶ 压缩 ──▶ 提纲 ──▶ 正文 ──▶ 事实校验 ──▶ (修正) ──▶ 发布
 (步骤3)     (步骤4)     (步骤5)   (步骤6)   (步骤7)    (步骤8)        │
                                                                     └─ 不通过则回到步骤6/7
```

### 步骤 3/4：标准人物档案 + 时间线（见 save-schema）
由解析与索引阶段产出。时间线已将人物相关数据统一为 `TimelineEvent[]`，每条带 `confidence` 与 `sourcePath`。

### 步骤 5：事件排序与压缩（**关键防溢出层**）
程序（而非模型）先完成：
- **去重**：同一事件的多处记录合并。
- **合并连续任期**：相邻的同一头衔/职位任期合并为一段。
- **合并重复头衔**：同名头衔多次出现只保留一份周期集合。
- **过滤无叙事价值事件**：剔除纯系统噪声（如短期无意义 buff）。
- **重要度打分**：依据"是否改变人生走向"给事件赋权（婚姻、继承、战争、囚禁、流亡、重大成败、死亡处境权重高；日常特质微调权重低）。
- **控制上下文长度**：按 `LLM_CONTEXT_HINT` 截断/精选，保留高分事件，绝不把几百条琐碎数据全交给模型。

产出：`CompressedProfile`（精简后的档案 + 精选时间线，附带每条的 confidence）。

### 步骤 6：生成传记提纲（第一次模型调用）
**只让模型生成结构化提纲**，不写正文。Prompt 约束：
- 输入：压缩后的档案摘要 + 精选时间线（事件 ID + 标题 + confidence + 日期）。
- 输出：严格的 JSON `BiographyOutline`，章节建议为：出身 / 少年时期 / 初入宫廷 / 婚姻与联盟 / 获得封地 / 统治时期 / 战争与危机 / 晚年 / 身后评价（可按人物实际经历增删）。
- **硬约束**：每个章节的 `eventIds` 必须非空且全部来自输入时间线；不得引用不存在的事件 ID；不得为提纲编造新事件。

提纲示例：
```json
{
  "profileId": "12345",
  "style": "vernacular_annals",
  "chapters": [
    {"id":"ch1","title":"出身","eventIds":["ev_birth","ev_dynasty"],
     "summary":"勃艮第公爵宫廷旁支，二十七岁前籍籍无名。"},
    {"id":"ch2","title":"婚姻与联盟","eventIds":["ev_marry_01","ev_court_enter"],
     "summary":"通过与公爵之女联姻首次进入权力中心。"}
  ]
}
```

### 步骤 7：生成正文（第二次模型调用）
- 输入：提纲 + 对应事件的完整描述（含 confidence 标注）。
- 输出：严格的 JSON `Biography`，每章 `content` 为白话纪传体正文，`eventIds` 追溯本章依据。
- 文风默认 `vernacular_annals`（白话纪传体）：现代中文、有历史叙事感、不堆砌古文、不写成游戏战报、不逐条复述属性、不过度赞美、可评价选择与后果、对缺点失败保持客观。
- 可选文风：`serious_biography` / `medieval_chronicle` / `family_memoir` / `concise_profile` / `cold_historian`。
- **inferred 信息**在正文里必须体现不确定性措辞；**uncertain** 一般不进入正文。

### 步骤 8：事实校验（自动，不通过则要求模型修正）
程序对生成结果做规则校验，发现问题**自动要求模型修正**，而不是直接展示错误内容。校验规则（来自规范第四节）：

| 规则 | 检查内容 | 触发即视为问题 |
|---|---|---|
| 时间一致性 | 事件日期是否矛盾 | 出现时间倒置（如死亡后还有事件） |
| 生死时序 | 子女是否生于父母死亡之后 | 是 → 错误 |
| 头衔归属 | 是否把未持有的头衔写给主人物 | 是 → 错误 |
| 战争归因 | 是否把敌方发动的战争写成主人物发动 | 是 → 错误 |
| 虚构内容 | 是否出现不存在的战役、地点、对白、心理活动 | 是 → 错误 |
| 推断当事实 | 是否把 inferred/uncertain 写成确定事实 | 是 → 错误 |
| 结构化合规 | 每章 `eventIds` 是否非空且全部存在 | 否 → 错误 |
| JSON 健壮性 | 模型返回是否合法 JSON | 否 → 重试/恢复，不崩溃 |

校验产出 `FactCheckResult`：`pass` 或 `needs_revision`。`needs_revision` 时把 `issues` 连同原文回喂模型，要求只修正问题、不改其他，最多重试 N 次；仍失败则向用户报告并保留草稿。

## 2. Prompt 设计要点

- **系统提示**固定声明角色与禁区（史官、只写证据、禁虚构对白/内心/战役细节、推断须显式标注）。
- **用户提示**只注入压缩档案与时间线，绝不注入原始存档字符串。
- 两次调用职责分离：提纲负责"结构 + 事件映射"，正文负责"文采 + 追溯"。
- 所有模型输出强制 JSON（带 schema 约束或后置解析），非法 JSON 触发重试。
- 温度默认 0.7，可在设置页调节；远程模型需 `LLM_ALLOW_REMOTE=true`。

---

## 3. 生成历史与可复现

- 每次生成记录：profileId、style、modelName、prompt 指纹、profileDigest（压缩档案哈希）、时间戳。
- 支持：重新生成、修改文风、编辑并保存、导出（Markdown / HTML，Phase 4）。
- 用户编辑后的正文与原始生成版本分别保存，便于对比。

## 4. 反虚构自检清单（发布前人工/程序复核）

- [ ] 每段正文至少关联一个真实事件 ID？
- [ ] 所有日期、头衔、配偶、子女均能在 Profile 中找到依据？
- [ ] 是否出现引号内的具体对白？→ 若无证据则删除。
- [ ] 是否描写了"心想/暗暗发誓"等内心活动？→ 若无证据则删除。
- [ ] inferred 事件是否被写成确定事实？→ 改为"可能/据推断"。
- [ ] uncertain 信息是否误入正文？→ 移至不确定提示面板。
